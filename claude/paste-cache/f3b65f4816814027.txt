Summary

Production Sidekiq has been intermittently failing with
OpenSSL::SSL::SSLError: SSL_read: (null) (tls_retry_write_records failure)
during scheduled-job enqueue and the job-dispatch loop. Root cause:
redis-rb 4.8.1's pure-Ruby driver routes reads through Ruby's
OpenSSL::Buffering, and the resulting OpenSSL::SSL::SSLError is
not a Redis::BaseConnectionError — so redis-rb's
ensure_connected retry list doesn't catch it; it propagates to
Sidekiq's worker layer and surfaces in NewRelic.

This PR upgrades to redis 5.4.1 + redis-client 0.28.0 +
sidekiq 7.3.10 + sidekiq-pro 7.3.7. redis-client doesn't go
through Ruby's OpenSSL::Buffering; connection errors are wrapped as
RedisClient::ConnectionError and uniformly retried by Sidekiq 7's
pool wrapper. The architectural path through which the production
exception reached the application layer no longer exists.

Coupled with the gem upgrade, config/environments/{production,development}.rb
must be updated in the same deploy: redis-client 0.28 rejects
:network_timeout and :tcp_keepalive at boot with
unknown keyword: :tcp_keepalive. Replaced with the split timeouts
(:connect_timeout, :read_timeout, :write_timeout).

The PR also includes:

    A local mTLS Redis docker-compose replica (redis/gen-certs.sh,
    docker-compose.yml, generated redis/tls/redis.env) that mirrors
    the production TLS posture so the dev stack exercises the exact same
    env-var → PEM → OpenSSL load path as production.
    redis/README.md — focused developer onboarding for the local
    mTLS setup (quick-start, troubleshooting, reference).
    redis/INVESTIGATION.md — full investigation report (the bug,
    why it propagates, the validated mitigation, the testing campaign,
    the rollout plan, a pre-deploy checklist).
    Companion fixes from the upgrade-compat audit: 22 migration files
    annotated with ActiveRecord::Migration[X.Y] (Rails 5+ requirement),
    app/services/frederick_client/request_service.rb return →
    next inside Campaign.transaction (Rails 6.1 deprecation),
    spec/services/frederick_client/request_service_spec.rb legacy
    .stub → allow().to receive (×2), and a silence_warnings { }
    wrap around an intentional re-load in
    spec/resources/api/v2/campaign_resource_spec.rb.

Aggregate validation on the new stack:
~18,000 Sidekiq-pool ops + ~50 write-bursts + ~315 deliberate
CLIENT KILLs + 1 full server bounce → 0 worker-layer errors. 0
OpenSSL::SSL::SSLError of any kind. Includes a 25-minute exhaustive
soak against redis:6.2-alpine (production-exact server version)
producing 11,875 pool ops + 39 bursts + 0 errors.

Does this PR introduce a breaking change?                                                                                                                                                 
                                                                                                                                                                                          
Yes — at the infrastructure / dependency layer, not the application                                                                                                                       
API. Two specific items:                                                                                                                                                                  
                                                                                                                                                                                          
1. Coupled gem + config change. The new gems                                                                                                                                              
(redis-client 0.28) reject the old config keys at boot. The                                                                                                                               
gem upgrade and the config update must land in the same deploy.                                                                                                                           
This PR is structured so that's automatic — both changes are in                                                                                                                           
the same merge commit.                                                                                                                                                                    
2. Sidekiq 7 connection footprint. Sidekiq 7 opens 15 Redis                                                                                                                               
connections per process (10 internal + 5 default) vs ~7 on                                                                                                                                
Sidekiq 6 — multiply by your sidekiq replica count. Verify managed                                                                                                                        
Redis MAXCLIENTS headroom before deploy.                                                                                                                                                  
                                                                                                                                                                                          
Application-level changes:                                                                                                                                                                
- Worker code paths unchanged. Sidekiq::Worker is still aliased to                                                                                                                        
Sidekiq::Job in v7. super_fetch!, sidekiq_retries_exhausted,                                                                                                                              
and default_job_options APIs are preserved.                                                                                                                                               
- Rails 6.1 LTS unchanged. Ruby 3.3.10 unchanged.

Are there special deployment instructions?                                                                                                                                                
                                                                                                                                                                                          
Yes — follow redis/INVESTIGATION.md Appendix A1 (pre-deploy                                                                                                                               
verification checklist). Highlights:                                                                                                                                                      
                                                                                                                                                                                          
1. Boot-time verification — confirm Sidekiq logs show                                                                                                                                     
Sidekiq 7.3.10 connecting to Redis with options {... :ssl=>true, :connect_timeout=>5, :read_timeout=>5, :write_timeout=>5, :reconnect_attempts=>3 ...} for both the internal and          
default pools. If you see unknown keyword: :tcp_keepalive —                                                                                                                               
the config didn't deploy with the gems; abort.                                                                                                                                            
2. Confirm Sidekiq Pro 7.3.7, commercially licensed. and                                                                                                                                  
SuperFetch[default] activated log lines appear.                                                                                                                                           
3. Soak in staging ≥ 24 hours before promoting to production.                                                                                                                             
Goal: cross at least one full TLSv1.3 session-ticket rotation                                                                                                                             
window. Watch NewRelic for any                                                                                                                                                            
OpenSSL::SSL::SSLError (tls_retry_write_records) recurrence —                                                                                                                             
should drop to zero.                                                                                                                                                                      
4. Production promotion on a non-peak window. Watch NewRelic                                                                                                                              
error rate and Rails.cache hit rate for the first hour.                                                                                                                                   
5. Optional, post-stabilization defense-in-depth: bump                                                                                                                                    
connection_pool to ~> 2.5 and add idle_timeout: 30                                                                                                                                        
(§6 option 2 in redis/INVESTIGATION.md).                                                                                                                                                  
                                                                                                                                                                                          
Rollback plan: revert the merge commit. Gems and config revert                                                                                                                            
atomically, restoring the prior stack.
